# 推量发接入 · 发布失败处理与避坑经验

> 配套《推量发开放接口文档》（同目录 `推量发开放接口文档.md`）。本文是**接入方实战经验**，重点是
> **Webhook 状态机的正确实现**与**各类失败的兜底处理**——这些是文档接口说明之外、真实接入时最容易踩的坑。
> 章节号引用均指 API 文档对应小节（如 §4.7、§6.2、§8）。

适用对象：任何基于该 SDK 实现「账号授权 + 一键发布 + 任务监控」的接入方（含 AI 直接据此生成代码）。

---

## 1.（最重要）任务状态机：`publishProcess` 的 `stageStatus=fail` 也是终态失败

**现象**：发布抖音视频，收到一条 `publishProcess`（`stages=upload`、`stageStatus=fail`、`errorMessage="视频下载失败:..."`），
但任务一直停在「发布中」，迟迟不翻成「失败」。

**根因**：很多接入方（含早期我方实现）只把 `publishResult` 当终态、把 `publishProcess` 当「进度」仅做展示。
但**上传/下载等早期阶段失败时，上游只推一条 `publishProcess(stageStatus=fail)`，不会再补 `publishResult`**。
于是只认 `publishResult` 的实现会让该任务永远卡「发布中」，直到 ~1 小时超时兜底（§6.2 末）才被动翻终态。

**正确做法**：收到 `publishProcess` 且 `stageStatus=fail` → **当作该子任务（subTask）的终态失败处理**，
与处理 `publishResult(stageStatus=fail)` 完全一致：写入 `result_summary` 该条为 failed + `errorMessage`、
重算 success/failed 计数、落整任务 status、发通知。实现上可直接把这条 `publishProcess(fail)` 转交给
`publishResult` 的同一套终态逻辑。

```
收到 webhook:
  event == publishResult                       -> 终态逻辑（success/fail）
  event == publishProcess && stageStatus==fail -> 终态逻辑（按 fail 处理）   ← 关键，别只记进度
  event == publishProcess && 其它               -> 仅更新进度，不改 task 状态
```

**整任务终态判定**：按子任务维度统计——`done = success + failed`；当 `done >= total_count` 时：
全部成功→`success`、全部失败→`failed`、部分→`partial`；否则保持 `publishing`。

**乱序/迟到保护**：上游偶尔乱序推送。**某子任务已是 success/failed 终态后，迟到的 `publishProcess` 进度必须丢弃**，
否则会出现「最终：失败，但进度仍显示上传中」的脏数据。

**超时兜底**：上游 ~1h 后会补一条终态 `publishResult`，所以你**总会**收到最终结果；但**不要依赖它做实时 UX**——
按上面规则在收到 `fail` 时就立即落终态。

## 2. 对账匹配：本地任务 ID 在 `callBackData.external_content_id`

经网关回流的 webhook，`callBackData` 里同时有 `task_id` 与 `external_content_id`：

- **`external_content_id` = 你发布时传入的本地任务 ID** —— 匹配本地任务用它。
- `task_id` 是网关侧任务 ID，**不是**你的本地 ID，别拿它查本地库。

健壮写法：本地任务 = `external_content_id ?? task_id`（兼容历史/直连）。
子任务匹配用 `event.taskId`（= 你发布时传的 `sub_task_ids[i]`，缺省时取 `POST /publish` 响应 `account_snapshot[].subTaskId`）。

## 3. Webhook 找不到对应任务 → 直接丢弃（必须做的兜底）

任务可能被用户删除、属于历史数据、或 ID 未知。**所有 webhook handler 在按 `external_content_id` 找不到本地任务时，
应静默 return（丢弃该消息），不要报错、不要新建幽灵记录、不要 5xx 给上游**（5xx 会触发上游重试，放大问题）。

幂等要求：同一子任务可能收到多条（progress→result、乱序、超时补发）：

- `result_summary` 按 `subTaskId` **upsert**（存在则更新、不存在则追加），计数每次按全量重算，保证幂等。
- 终态通知按 `task_id` 去重（如「1 天内同任务只发一次」），避免重复打扰。

## 4. 素材 URL 必须「上游可下载」（`视频下载失败` / `获取视频大小失败` 的根因）

**现象**：`errorMessage="视频下载失败:<url>"`，或同步返回 `50200` + `获取视频大小失败: HTTP 405`。

**本质**：`video_url` / `cover_urls` / `media_urls` 必须是**公网可访问的直链**，且**上游服务器能直接 GET 下载**
（最好支持 HTTP `Range` 与 `HEAD`，上游常先 HEAD 取大小、再 Range 拉取）。

**高频坑（浏览器能打开 ≠ 上游能下载）**：

- **家宽 / 住宅宽带 IP**：运营商默认封禁公网入站 80/443，外部根本连不进来；你本机浏览器能开是因为走了**同网 NAT 回环（hairpin）**。
  典型表现：你浏览器正常、上游连接**超时**（提交后约 10 分钟才回 `下载失败`，是超时而非秒回）。
- **内网 / 需登录 / 需签名 / 防盗链 / 仅 HTTP** 的链接，上游匿名 GET 取不到。
- **TLS 证书链不完整**：浏览器会自动补中间证书，严格的服务端 HTTP 客户端（Go/Java/Python）握手直接失败。

**诊断步骤**（务必从**外部**视角，不要在自己机器上测，否则会被 hairpin 误导）：

```bash
# 在一台「外部云 VPS」上（模拟上游网络）执行：
nslookup your-asset-domain                       # 看解析到的 IP，是否是家宽/住宅 IP
curl -I   https://your-domain/path/video.mp4     # HEAD：期望 200 + Content-Length + Accept-Ranges: bytes
curl -r 0-1048575 -sv https://.../video.mp4 -o /dev/null   # Range：期望 206 + Content-Range
curl -v --max-time 60 -o /tmp/x.mp4 https://.../video.mp4   # 整文件：看是否超时/重置
echo | openssl s_client -connect your-domain:443 -servername your-domain   # 看证书链 Verify return code: 0 (ok)
```

- 若**超时/连不上** → 是入站可达性问题（家宽封禁 / 防火墙 / DNS 指向不可达 IP）。
- 若 **4xx/403** → 防盗链 / 需鉴权 / 路径错。
- 若证书 `verify error` → 服务端缺中间证书（补全 fullchain）。

**正解**：素材托管在**真正公网可达**的地方——对象存储（OSS / COS / R2 等）/ CDN / 有公网 IP 且（国内）已 ICP 备案的服务器。
不要用家宽自建服务直链给上游回源。

## 5. 平台风控类失败 → 站内直接「解除发布风控」（抖音）

部分失败不是内容问题，而是**平台风控/验证**。典型（抖音）：

```
errorMessage: "发布失败:官方平台检测到您的账号存在风险，请先前往《创作者中心》里登录后单独发布一个作品，
              发布时会跳出验证，验证通过即可一键发布。"
```

**不要只给一个「去创作者中心」的跳转链接**——平台提供了风控解除接口，可在你自己的界面里直接完成验证、解除（见 API 文档 §4.7）：

1. **查状态** `GET /accounts/{id}/risk-status` → `{risk_status, check_methods:[{type,name}]}`（type=`password`/`smscode`）。
2. 用户二选一：
   - `password`：让用户**当场输入社媒登录密码** → `POST /accounts/{id}/risk-confirm {method:"password", password}`。
   - `smscode`：`POST /accounts/{id}/risk-sms`（发验证码，返回掩码手机号）→ 用户填码 → `risk-confirm {method:"smscode", code}`。
3. `code=0` 即受理，稍后可重新发布。

**触发**：前端按 `errorMessage` 关键词（含「创作者中心 / 存在风险 / 风控 / 验证 / 单独发布」）识别为风控类失败，在失败处给「解除发布风控」入口打开上面的流程；同时在「账号管理」对抖音号也提供主动「检测/解除风控」入口。

**安全**：`password` 是用户社媒登录密码——**当场采集、单次使用、绝不持久化/不打日志**（与扫码授权密码同等处理）。解除依赖账号 `active`；`expired` 需先重新扫码授权。

## 6. 账号登录态失效（expired）→ 引导重新扫码

详见 API 文档 §4.6。要点：

- 同步操作（取分类 §4.5 / 发布 §6）若报登录失效，会返回错误信封，且该账号被置为 `expired`（随后 `GET /accounts` 可复核）。
- 也可能由 `accountStatus` webhook 异步推 `expired`。
- 恢复：引导用户对**同一 `platform_code`** 重走 `POST /auth/start` 扫码；成功后 `account_id` 不变、`status` 回 `active`。
- UI 务必对 `expired` 账号显著标识并给「重新授权」入口；本平台无静默续期接口，必须用户重新扫码。

## 7. 内容分类预加载的兜底（别把「空分类」当致命错误）

取分类（§4.5）时：

- **可选分类平台**：上游可能返回空列表（偶尔以非 0 业务码 + 空 `list` 表达「该账号此类型无分类」）。
  这是**正常**的，不要弹致命错误，按「无分类」继续即可。
- **必填分类平台**（§7.1 `category` 列带 `ᴿ`，如哔哩哔哩视频）：取不到分类多半是**登录态失效**——
  应就地提示并引导重新授权（见 §6），而不是让用户对着空下拉框干瞪眼。

## 8. 同步失败 vs 异步失败：先判 HTTP 状态

- **同步失败**（任务未受理，不会有 webhook）：`POST /publish` 直接返回错误信封——
  `40000`（参数/内容不合规）、`50200`（平台处理失败，如素材取不到）、或登录态失效。先判 HTTP 状态再决定是否进入「等 webhook」流程。
- **异步失败**（已受理）：返回 `status=publishing` 后，靠 webhook 判终态（见 §1）。

不要把同步错误当「发布中」挂起，也不要对同步已失败的任务去等 webhook。

## 9. 实现自检清单（Checklist）

- [ ] `publishProcess(stageStatus=fail)` 已按**终态失败**处理（不只是记进度）。
- [ ] 整任务终态按子任务 success/failed 计数判定（全成功/部分/全失败）。
- [ ] 已终态子任务，迟到的 `publishProcess` 会被丢弃（防脏数据）。
- [ ] 本地任务匹配用 `callBackData.external_content_id`（不是 `task_id`）。
- [ ] 找不到任务的 webhook 静默丢弃，返回 2xx，不重试放大。
- [ ] `result_summary` 按 `subTaskId` upsert；终态通知按 task 去重（幂等）。
- [ ] 素材直链经**外部 VPS** 验证可下载（HEAD 200 / Range 206 / 证书链完整），不用家宽直链。
- [ ] 抖音风控类 `errorMessage` 提供站内「解除发布风控」入口（§4.7：查状态→密码/短信验证码→解除），密码不持久化。
- [ ] `expired` 账号显著标识 + 一键「重新授权」；同步操作报登录失效时置 expired。
- [ ] 取分类：可选平台空列表当正常、必填平台取不到引导重授权。
- [ ] Webhook 验签（HMAC + 300s 窗口）+ 尽快 2xx + 耗时转异步。
- [ ] 不依赖轮询；超时由上游 ~1h 兜底补终态（但 UI 实时性靠收到 fail 即落终态）。
